# Requirements contract

BA owns `requirements/<feature>.md`. Start from `docs/project-brief.md`; no detailed feature requirements have been agreed yet.

Use these sections when creating a feature specification:

- Metadata: feature slug, status, date, source/request, related artifacts.
- Goal and target user.
- In scope and out of scope.
- User journeys and stable requirement IDs.
- For each requirement: behavior, priority, and observable acceptance criteria (Given/When/Then where useful).
- Fields and validation; permissions and privacy rules.
- Phone/laptop interactions and relevant UI states.
- Business rules, including dates/timezones where applicable.
- Confirmed decisions, labelled assumptions, and open questions.
- Change notes and handoff dependencies.

Keep IDs stable so design notes, architecture plans, and tests can reference them. Do not present proposed defaults as confirmed requirements.
